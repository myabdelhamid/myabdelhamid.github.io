Amtsbrief - AI Decoder for German Official Letters

Explains German official letters (Finanzamt, Bürgeramt, Krankenkasse, landlord, fines) in plain English: it finds the amounts and deadlines, shows the line each claim comes from, and puts the deadlines in your calendar

Project Overview

A live web app, built solo: you upload a photo or PDF of a German official letter, and it explains the letter in plain English, pulls out the amounts and deadlines, links every claim to the exact line it came from, and adds the deadlines to your calendar.

It's built around one rule: the model's output is never shown as fact until code has checked it against the letter. Anything that can't be verified is shown as "Couldn't verify" instead of as a guess.

How It Works

upload → preprocess → transcribe → extract → validate → store + calendar

  • • Preprocess: PDFs (digital or scanned), JPEG, PNG, WebP and HEIC become one image per page. EXIF is removed, so GPS data never leaves the server, and a PDF's text layer is ignored so it can't differ from what a person sees
  • • Transcribe: Gemini copies each page line by line with numbered line IDs (P1-L1, P1-L2, …)
  • • Extract: a second call fills a Pydantic schema, and every field carries a verbatim quote and the line IDs it came from
  • • Validate (plain code): cited lines must exist, quotes must match their lines, dates and amounts must parse and IBAN checksums must pass. A failed check gets one retry with specific feedback; anything still failing goes to "Couldn't verify"
  • • Deadlines: the model only extracts the wording ("innerhalb eines Monats nach Bekanntgabe"); code computes the date step by step, applying the 4-day receipt rule, month-end clamping, calendar periods and the weekend shift. Wording the code can't compute is never guessed

Design Decisions

  • • Transcription and extraction are separate calls, so every claim can cite transcript lines and code can verify those citations
  • • The LLM never does date math. Legal deadlines follow rules, and code applies them the same way every time
  • • No tools, no actions. The app informs and reminds; what to do about a letter is the user's decision. The model can only fill a schema

Prompt-Injection Defenses

A letter is untrusted input: anyone can print "ignore your instructions" on one. Six attack letters based on published attacks (indirect injection, hidden text, invoice bank-detail swaps, output smuggling) are part of the test set.

  • • Detect and warn: lines addressed to a machine ("ignore previous instructions", fake end markers) are flagged and the user sees a warning. Anything citing those lines goes to "Couldn't verify", and an injected date never becomes a reminder
  • • Hardened transcription: the model copies every line, including text addressed to it, and follows none of it. Its thinking is capped, so a page can't make it think for minutes
  • • Spotlighting: in the extraction prompt the transcript is fenced as data and the flagged lines are named
  • • Own-words check: a URL, email, IBAN or phone number in a summary must appear in a trustworthy line of the letter, which stops "call 0900 …" from reaching the user

Evaluation

All numbers are from one run each, with Gemini Flash:

  • • Extraction (20 synthetic letters, 6 types): 140/140 fields correct, 19/20 letters fully verified
  • • Held-out real-format letters (7 letters, 1–3 pages): 48/49 fields correct, 5/7 fully verified
  • • Transcription: 99.4% of lines exact when ignoring dash style (90.4% strictly)
  • • Prompt injection (6 attack letters): 6/6 attacks blocked, 6/6 users warned, 42/42 fields correct
  • • False alarms: 0 injection warnings across all 27 normal letters

"Not fully verified" is mostly the system working as intended, for example a deadline counted from an undated event or an IBAN printed wrongly in the letter itself: the item is shown as "Couldn't verify" instead of as a guess.

Deployment & Privacy

  • • One container on Google Cloud Run: FastAPI serves both the API and the built React app
  • • Sign-in with Firebase Auth (Google); letters are stored in Firestore under each user's id, with a limit of 20 letters per user per day
  • • Every push to main runs the tests and deploys through GitHub Actions, authenticated with Workload Identity Federation, so no key is stored in the repository
  • • Only the analysis is stored, never the uploaded file; logs contain ids and counts, never letter text; users can delete any letter
