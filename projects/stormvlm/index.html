The Core Idea

Cameras fail in fog for a physical reason: the geometry is never recorded. A vision-language model asked about a scene it can't see doesn't say "I can't tell". It confidently describes an empty road.

StormVLM's answer is not a bigger model, but more physics: fuse 4D radar into the scene, and make every perceptual claim the model makes checkable against physics. Everything the model asserts about distance, speed or risk is either pre-computed in Python or verified by it afterwards.

RQ1
Does 4D radar fusion measurably reduce hallucination in zero-visibility weather?
RQ2
Does a rigid JSON schema produce more reliable planning than free chain-of-thought?
RQ3
Is sensor fusion a cheaper route to safety than scaling model parameters?

From Six Radars to a Few Anchors

Six radar point clouds are brought into the vehicle's frame, filtered, and clustered into a handful of Radar Anchors, each with a position, speed, Doppler and confidence that the language model can reason over.

  1. 1
    Fuse
    6 sensors → one (N, 5) cloud [x, y, z, v, sensor], each transformed by its own extrinsics into the vehicle frame.
  2. 2
    Gate
    Keep returns within 200 m and ±3 m height.
  3. 3
    Cluster
    DBSCAN on the ground plane, ε = 0.6 m, min 3 points: 93.3% near-field recall against ground truth.
  4. 4
    Extract
    Centroid, max speed, mean Doppler, point count, the matching camera, and a confidence score.

Measuring What the Camera Can Really See

Using Koschmieder's law, contrast decays exponentially with distance: C(d) = C₀ · e−βd. Fitting the extinction coefficient β per weather condition turns "fog" into a measured, physical visibility limit.

Clear weather is the built-in control: its β is effectively zero, so the decay in the other conditions is atmospheric.

Catching Hallucination with Physics

With the real visibility limit known, every claim the model makes can be checked: if it says it can see an object that lies beyond the physical limit, that claim is provably impossible.

The RSS Safety Gate

Risk at the top end is not the model's to decide. Responsibility-Sensitive Safety (RSS) rules, applied identically in every pipeline, can force or cap the risk the model proposes.

Moving away
Diverging, falling behind or moving away
→ NO RISK
Outside the corridor
More than 3 m to the side and not closing in
→ NO RISK
RSS violated
A front object breaks the safe distance on both axes
→ HIGH (forced)
RSS satisfied
The model said HIGH, but RSS says the gap is safe
→ capped at MODERATE

The corridor rule never gets the last word: a cut-in starts outside the corridor, so the RSS check still runs and can escalate to HIGH. The gate also ignores the perception category, so pipelines differ only in which objects they keep, never in how they grade them.

A Planner That Can't Go Off the Rails

The action is generated by the VLM, but inside a strict structural envelope: one call decides, a second explains, and the explanation is written only after the action is fixed.

// decision call: the only accepted shape
{
  "critical_object_id": "Front_vehicle_2",
  "critical_risk": "HIGH",
  "action": "EMERGENCY_BRAKE"
}
action ∈ KEEP_SPEED · DECELERATE · EMERGENCY_BRAKE
  • • Candidates filtered in code: Only front objects that the safety gate hasn't cleared are shown, so the model can't pick one it never saw.
  • • Three fields, no free text: Naming the object and its risk before the action acts as a compressed chain of thought.
  • • Strict parsing: Invalid JSON, an unknown action or an invented object ID is counted as a failure, never silently repaired.
  • • Fails toward braking: If a call ever fails, the fallback maps the worst risk present to braking, not to keeping speed.
49 of 49 decision calls returned valid JSON with an allowed action and a real object from the candidate list. The fallback never had to fire.
